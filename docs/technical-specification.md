# Техническое задание BudgetPlanner

## 1. Общая информация

**Название:** BudgetPlanner (рабочее)

**Версия документа:** 0.2, черновик

**Целевая версия продукта:** 1.0

**Тип продукта:** Android-приложение, все данные хранятся только на телефоне

**Основной сценарий:** пользователь видит, сколько денег можно потратить сегодня, чтобы дожить до следующего дохода. Траты попадают в приложение автоматически из уведомлений банка или вводятся вручную.

BudgetPlanner не подключается к банку, не просит логины, пароли и данные карт и не может проводить операции. Приложение читает только текст уведомлений банковского приложения, которые и так появляются на экране телефона. Аккаунта и собственного сервера нет. Интернет нужен только для необязательного ИИ-помощника.

## 2. Цель продукта

Создать личный инструмент для контроля расходов, которым удобно пользоваться каждый день, потому что почти ничего не нужно вводить руками.

Версия 1.0 должна решать пять задач:

1. показать на главном экране одну понятную цифру: сколько можно потратить сегодня;
2. учитывать траты и доходы без ручного ввода, по уведомлениям банка;
3. заранее резервировать обязательные платежи (аренда, связь, подписки);
4. показывать, куда уходят деньги, по категориям и по дням;
5. отвечать на вопросы о расходах обычным языком через ИИ-помощника.

## 3. Границы системы

### 3.1 Компоненты

- Android UI на Jetpack Compose;
- доменный слой с расчётом бюджета, без зависимостей от Android;
- зашифрованная локальная база операций (Room + SQLCipher);
- сервис чтения уведомлений банков (`NotificationListenerService`) и парсеры текстов по банкам;
- ИИ-модуль с заменяемым провайдером модели (GigaChat по умолчанию);
- виджет рабочего стола (Glance);
- фоновые задачи (WorkManager): пересчёт дня, напоминания, очистка.

### 3.2 Схема работы

```text
+-------------------------------+
| Приложение банка              |
| показывает push-уведомление   |
+---------------+---------------+
                |
                v
+------------------------------------------------+
| BudgetPlanner                                  |
|                                                |
| NotificationListenerService                    |
|   -> фильтр по пакетам банков                  |
|   -> парсер банка -> операция (без исходного   |
|      текста уведомления)                       |
|                                                |
| Domain: расчёт периода и «можно сегодня»       |
| Room + SQLCipher, DataStore, Android Keystore  |
| Compose UI, Glance-виджет, WorkManager         |
|                                                |
| AI: LlmProvider -> инструменты над локальными  |
|     данными                                    |
+-----------------------+------------------------+
                        |  только если ИИ включён,
                        |  только агрегаты
                        v
              +-------------------+
              | GigaChat API      |
              +-------------------+
```

### 3.3 Условия работы

- Android 10 (API 29) и новее, `targetSdk` 37.
- Пользователь вручную выдаёт доступ к уведомлениям в системных настройках.
- Без интернета работает всё, кроме ИИ-помощника.
- Валюта версии 1.0: только рубли.

## 4. Термины

| Термин | Значение |
|---|---|
| Операция | Трата, доход, возврат или перевод с суммой, датой, категорией и источником |
| Источник | Как операция попала в приложение: вручную или из уведомления |
| Черновик | Операция из уведомления, которую пользователь ещё не подтвердил |
| Период | Отрезок от текущего дохода до следующего (стипендия, зарплата) |
| Обязательный платёж | Плановый расход внутри периода, деньги на него резервируются заранее |
| Резерв | Сумма неоплаченных обязательных платежей до конца периода |
| Дневной лимит | Сколько в среднем можно тратить в день до конца периода |
| «Можно сегодня» | Дневной лимит минус сегодняшние траты |
| Правило категории | Запомненное соответствие «магазин → категория» |
| Остаток банка | Сумма на карте, которую банк указал в последнем уведомлении |
| Корректировка | Операция, которая выравнивает расчёт приложения с реальным остатком банка |
| Провайдер модели | Реализация интерфейса `LlmProvider` (GigaChat, YandexGPT, локальная модель) |

## 5. Пользовательские сценарии

### 5.1 Первый запуск

1. Пользователь видит экран с объяснением: что делает приложение и что оно не получает доступ к банку.
2. Вводит, сколько денег у него сейчас есть на период, и дату следующего дохода.
3. Добавляет обязательные платежи до этой даты или пропускает шаг.
4. Приложение предлагает включить автоимпорт: объясняет, какие уведомления читаются и что сохраняется, затем открывает системные настройки доступа к уведомлениям.
5. Предлагает защиту входа по отпечатку или PIN-коду.
6. Открывается главный экран с суммой «можно сегодня».

### 5.2 Покупка с автоимпортом

1. Пользователь платит картой, банк присылает уведомление «Покупка 450 ₽, Пятёрочка».
2. Приложение распознаёт сумму, магазин и тип операции, не сохраняя исходный текст.
3. Если для магазина есть правило категории, операция сохраняется сразу. Если нет, создаётся черновик.
4. Сумма «можно сегодня» на главном экране и в виджете уменьшается.

### 5.3 Подтверждение черновиков

1. На главном экране видна плашка «3 операции ждут категорию».
2. Пользователь выбирает категорию для каждой. Приложение предлагает запомнить правило для магазина.

### 5.4 Ручной ввод

1. Пользователь нажимает «+», вводит сумму, выбирает категорию, при желании добавляет комментарий.
2. Операция сохраняется с источником «вручную».

### 5.5 Перерасход

1. Траты за день превысили дневной лимит.
2. Главный экран показывает перерасход красным, приходит одно уведомление за день.
3. Завтра дневной лимит автоматически пересчитывается с учётом перерасхода.

### 5.6 Новый период

1. Наступает дата следующего дохода, либо из уведомления банка распознано зачисление, похожее на зарплату или стипендию.
2. Приложение предлагает начать новый период: подтвердить сумму и дату следующего дохода.
3. Итоги прошлого периода сохраняются в статистике.

### 5.7 Вопрос ИИ-помощнику

1. Пользователь спрашивает: «Хватит ли до стипендии, если куплю наушники за 3000?»
2. Модель вызывает локальный инструмент `simulate_purchase(3000)`, получает новый дневной лимит и отвечает обычным языком.
3. В модель уходят только результаты инструментов, а не база операций.

### 5.8 Пополнение

1. Банк присылает уведомление «Зачисление 2 000 ₽».
2. Приложение записывает доход, бюджет периода и дневной лимит растут.
3. Если сумма и отправитель похожи на стипендию или зарплату, приложение предлагает начать новый период.

### 5.9 Сверка с банком

1. Пришло уведомление «Покупка 450 ₽, Пятёрочка. Баланс 12 300 ₽».
2. По расчёту приложения на карте должно быть 12 750 ₽.
3. На главном экране появляется плашка: «Расхождение с банком 450 ₽». Пользователь открывает её и выбирает: записать разницу как трату без категории, найти пропущенную операцию или пропустить.

## 6. Функциональные требования

### FR-01. Операции

- Создание, редактирование и удаление операций вручную.
- Поля: сумма, тип (трата, доход, возврат, перевод), дата и время, категория, магазин или описание, комментарий, источник, признак «обязательный платёж».
- Суммы хранятся целым числом копеек (`Long`), без `Double`.
- Удалённая операция сразу пропадает из расчётов. Отмена удаления через snackbar в течение 5 секунд.

### FR-02. Категории

- Набор категорий по умолчанию: продукты, кафе и рестораны, транспорт, связь и интернет, развлечения, одежда, здоровье, подписки, переводы, другое.
- Свои категории с названием, иконкой и цветом.
- Категорию с операциями нельзя удалить, только скрыть.

### FR-03. Период и «можно сегодня»

Расчёт выполняется в доменном слое чистой функцией и полностью покрывается unit-тестами.

- Период длится от даты начала до даты следующего дохода. Дата следующего дохода в период не входит.
- `Бюджет периода` = стартовая сумма + доходы внутри периода. Возврат покупки уменьшает сумму трат, а не увеличивает доходы.
- `Осталось дней` = число дней от сегодня до даты следующего дохода, включая сегодня, минимум 1.
- `Доступно на начало дня` = бюджет периода − все траты до сегодняшнего дня − резерв на начало сегодняшнего дня.
- `Дневной лимит` = доступно на начало дня / осталось дней, округление вниз до рубля.
- `Можно сегодня` = дневной лимит − траты за сегодня, кроме оплаты обязательных платежей.
- Оплата обязательного платежа не уменьшает «можно сегодня»: деньги на него уже были в резерве.
- Неожиданный доход внутри периода сразу пересчитывает лимит.
- Если «можно сегодня» меньше нуля, показывается перерасход.
- Пересчёт при смене дня выполняется по фактической дате при открытии приложения и виджета, а не только фоновой задачей.
- Время берётся через внедряемый `Clock`, чтобы тесты могли управлять датой.

### FR-04. Обязательные платежи

- Список платежей: название, сумма, дата, повтор (разово, ежемесячно).
- Неоплаченные платежи до конца периода входят в резерв.
- Платёж отмечается оплаченным вручную или автоматически, если из уведомления пришла трата с похожими суммой и названием. Автосопоставление требует подтверждения.
- Напоминание за день до даты платежа.

### FR-05. Автоимпорт из уведомлений

- Работает через `NotificationListenerService`, включается пользователем отдельно.
- Обрабатываются только уведомления от пакетов из списка поддерживаемых банков. Все остальные отбрасываются сразу, без записи куда-либо.
- Для каждого банка свой парсер, реализующий общий интерфейс:

  ```kotlin
  interface BankNotificationParser {
      val bankId: String
      val packageNames: Set<String>
      fun parse(notification: BankNotification): ParsedOperation?
  }
  ```

- Обрабатываются и списания, и пополнения:

  | Тип в уведомлении | Пример | Что делает приложение |
  |---|---|---|
  | Покупка, оплата, списание | «Покупка 450 ₽, Пятёрочка» | Трата: уменьшает «можно сегодня» и «осталось» |
  | Исходящий перевод | «Перевод 500 ₽, Олег К.» | Трата в категории «Переводы», создаётся черновиком |
  | Пополнение, зачисление, входящий перевод | «Зачисление 9 000 ₽» | Доход: увеличивает бюджет периода и дневной лимит. Если похоже на стипендию или зарплату, предлагает начать новый период (сценарий 5.6) |
  | Возврат, отмена покупки | «Отмена покупки 450 ₽» | Уменьшает сумму трат |
  | Перевод между своими счетами | «Перевод между счетами 1 000 ₽» | Игнорируется, если это видно по тексту |
  | Перевод себе в другой банк | «−5 000 ₽» в одном банке и «+5 000 ₽» в другом за несколько минут | Склеивается в «перевод себе»: не трата и не доход. Если видна одна сторона — кнопка «Это перевод себе» в черновике, имя отправителя можно запомнить |

- Если в уведомлении указан остаток («Баланс 12 300 ₽», «Доступно 12 300 ₽»), парсер сохраняет его вместе с временем уведомления и последними 4 цифрами карты, если они есть. Остаток используется для сверки (FR-13).
- Исходный текст уведомления не сохраняется. В базу пишутся только разобранные поля.
- Защита от дублей: уникальный ключ уведомления плюс совпадение банка, суммы и магазина в окне 2 минут.
- При подключении сервиса проверяются уже показанные уведомления (`getActiveNotifications`), чтобы не пропустить пришедшие, пока сервис был отключён.
- Настройки показывают состояние: «автоимпорт работает» или «нет доступа к уведомлениям» с кнопкой перехода в системные настройки.
- Для прошивок, которые выгружают фоновые сервисы (Xiaomi, Huawei и другие), показывается подсказка про автозапуск и энергосбережение.
- Режим сбора образцов для разработки парсеров по умолчанию выключен. Если включить, исходные тексты уведомлений банков сохраняются локально с замаскированными цифрами карт и счетов и удаляются через 24 часа.
- Первым поддерживается Сбер, следующими — Т-Банк и Альфа-Банк (решение по вопросу 1 раздела 17). Каждый банк добавляется новым парсером без изменения других слоёв.

### FR-06. Автокатегоризация

- Подтверждая категорию черновика, пользователь может запомнить правило «магазин → категория».
- Новая операция из уведомления сначала проверяется по правилам.
- Если правила нет, а магазин есть во встроенном словаре популярных магазинов, черновик получает категорию из словаря как подсказку с подписью «Знакомый магазин». Операция остаётся черновиком до подтверждения пользователем.
- Если правила нет и ИИ включён, модель может предложить категорию. Предложение не применяется без подтверждения пользователя.
- Правила можно просматривать, менять и удалять.

### FR-07. Статистика

- Расходы по категориям за текущий период и за календарный месяц (кольцевая диаграмма).
- Расходы по дням с линией дневного лимита (столбчатая диаграмма).
- Сравнение с прошлым периодом: где потрачено больше и меньше.
- Топ магазинов по сумме.
- Итоги завершённых периодов.

### FR-08. ИИ-помощник

- Чат с моделью, история диалогов хранится локально.
- По умолчанию выключен. При включении пользователь видит, какие данные уходят в модель.
- Модель не получает базу целиком. Она вызывает локальные инструменты и получает только их результаты:

  | Инструмент | Что возвращает |
  |---|---|
  | `get_period_status()` | Бюджет, резерв, потрачено, дневной лимит, «можно сегодня», дней до дохода |
  | `get_spending(category?, from, to)` | Сумма и число операций |
  | `get_spending_by_category(from, to)` | Суммы по категориям |
  | `get_top_merchants(from, to, limit)` | Магазины с наибольшими тратами |
  | `simulate_purchase(amount)` | Новый дневной лимит после гипотетической покупки |
  | `compare_periods()` | Разница по категориям с прошлым периодом |

- Все инструменты только читают данные. Изменять операции через ИИ в версии 1.0 нельзя.
- Настройка «не отправлять названия магазинов»: инструменты отдают только категории и суммы.
- Провайдер модели скрыт за интерфейсом `LlmProvider`, чтобы GigaChat можно было заменить на YandexGPT или локальную модель без изменения остального кода.
- Учёт израсходованных токенов и предупреждение при приближении к лимиту бесплатного тарифа.
- При ошибке сети или исчерпанном лимите чат показывает понятное сообщение. Остальные функции приложения продолжают работать.

### FR-09. Виджет

- Glance-виджет: «можно сегодня», дней до дохода, кнопка быстрого добавления траты.
- Обновляется после каждой новой операции и при смене дня.

### FR-10. Защита входа

- Вход по биометрии или PIN-коду, включается в настройках.
- Блокировка после ухода в фон на заданное время (сразу, 1 минута, 5 минут).
- Опционально скрытие содержимого в списке недавних приложений (`FLAG_SECURE`).

### FR-11. Экспорт и резервная копия

- Экспорт операций в CSV за выбранный период.
- Резервная копия в зашифрованный файл с паролем пользователя и восстановление из неё.

### FR-12. Уведомления приложения

- Перерасход дневного лимита (не чаще одного раза в день).
- Напоминание об обязательном платеже.
- Предложение начать новый период.
- Расхождение с банком (FR-13).
- Каждый тип отключается отдельно.

### FR-13. Сверка с банком

Нужна, потому что приложение не видит счёт и может разойтись с ним: оплата наличными, пропущенное уведомление, комиссия или автоплатёж без пуша.

- Точка отсчёта: первый остаток, пришедший в уведомлении по карте, или сумма, введённая пользователем вручную.
- `Ожидаемый остаток` = остаток в точке отсчёта + пополнения − списания по этой карте после неё.
- Каждый новый остаток из уведомления сравнивается с ожидаемым. Если разница больше 1 ₽, на главном экране появляется плашка «Расхождение с банком N ₽».
- Варианты для пользователя: записать разницу корректировкой (банк показывает меньше — трата без категории; больше — доход), открыть операции за период, чтобы найти пропущенную, или пропустить.
- Корректировка без подтверждения пользователя не создаётся. Корректировка входит в расчёт «можно сегодня» как обычная операция.
- После решения точкой отсчёта становится новый остаток банка.
- Остатки разных карт сверяются отдельно по последним 4 цифрам. Если цифр в уведомлении нет, все операции банка считаются одной картой.
- Ручная сверка: кнопка «Сверить с банком» на экране периода, пользователь вводит реальный остаток, дальше тот же сценарий.
- Автоматическую сверку можно выключить в настройках.

## 7. Экраны

### 7.1 Онбординг

Объяснение продукта и приватности, ввод стартовой суммы и даты дохода, обязательные платежи, включение автоимпорта, включение защиты входа.

### 7.2 Главный экран

- Крупно: «можно сегодня». Под ним дневной лимит и дней до дохода.
- Прогресс периода: потрачено, резерв, осталось.
- Плашка черновиков, если они есть.
- Плашка расхождения с банком, если оно есть (FR-13).
- Последние операции.
- Кнопка «+».

### 7.3 Операции

Список с группировкой по дням, поиск, фильтр по категории и источнику.

### 7.4 Операция

Создание и редактирование. Для операций из уведомления показывается источник «из уведомления банка».

### 7.5 Черновики

Очередь неподтверждённых операций с быстрым выбором категории и галочкой «запомнить для этого магазина».

### 7.6 Статистика

Диаграммы и итоги из FR-07, переключатель «период / месяц».

### 7.7 Период и платежи

Текущий период, дата дохода, список обязательных платежей, кнопка «начать новый период», кнопка «Сверить с банком» и время последней сверки.

### 7.8 ИИ-помощник

Чат, подсказки готовых вопросов, индикатор израсходованных токенов.

### 7.9 Настройки

Категории и правила, автоимпорт и его состояние, автоматическая сверка с банком, ИИ и ключ авторизации, защита входа, уведомления, экспорт и резервная копия, «удалить все данные».

## 8. Архитектура

### 8.1 Общий подход

Clean Architecture и MVVM. Room, Android API и сетевой клиент не проникают во ViewModel и доменный слой.

- **domain:** модели, расчёт бюджета, use cases, интерфейсы репозиториев и `LlmProvider`. Чистый Kotlin, тестируется на JVM.
- **data:** Room, DataStore, реализация репозиториев, хранение ключей.
- **notifications:** сервис, фильтр пакетов, парсеры банков. Парсеры — чистый Kotlin.
- **ai:** клиент GigaChat, реализация инструментов, цикл «запрос → вызов функции → результат → ответ».
- **ui:** экраны Compose, ViewModel, навигация, тема.
- **widget:** Glance.

### 8.3 Цикл ИИ-помощника

1. Приложение отправляет сообщения диалога и описания инструментов в поле `functions` с режимом `function_call: "auto"`.
2. Если модель возвращает `finish_reason: "function_call"`, приложение выполняет инструмент локально.
3. Результат добавляется в историю сообщением с ролью `function`, запрос повторяется.
4. Цикл ограничен 5 вызовами инструментов на один вопрос.

### 9.3 GigaChat API

- Получение токена: `POST https://ngw.devices.sberbank.ru:9443/api/v2/oauth`, заголовки `Authorization: Basic <ключ авторизации>` и `RqUID` (uuid4), тело `scope=GIGACHAT_API_PERS`. Токен живёт 30 минут, кэшируется в памяти и обновляется заранее.
- Запросы к модели: `POST https://api.giga.chat/v1/chat/completions` с `Authorization: Bearer <токен>`.
- Вызов функций: поля `functions` и `function_call`, ответ с `function_call` и `finish_reason: "function_call"`, результат передаётся сообщением с ролью `function`.
- Для TLS нужен корневой сертификат НУЦ Минцифры. Он кладётся в `res/raw` и подключается в `network_security_config` **только для доменов GigaChat** (`domain-config`), а не для всего приложения.
- Ключ авторизации пользователь получает сам в личном кабинете GigaChat и вводит в настройках. В код и репозиторий ключ не попадает.
- Бесплатный режим для физлиц: 365 млн токенов на 12 месяцев, один поток. С 1 сентября 2026 новых клиентов переводят на cloud.ru, доступность Freemium проверяется при регистрации.

## 10. Безопасность и приватность

### 10.1 Защищаемые данные

- история операций, суммы и магазины;
- остатки и бюджет;
- ключ авторизации GigaChat;
- ключ шифрования базы;
- остатки банка и последние 4 цифры карт (хранятся только в зашифрованной базе и не передаются в ИИ);
- образцы уведомлений в режиме разработки.

### 10.2 Угрозы и меры

| Угроза | Мера |
|---|---|
| Приложение видит все уведомления телефона, включая мессенджеры | Обработка только пакетов из списка банков, остальное отбрасывается сразу, без логирования |
| Утечка текста уведомлений | Исходный текст не сохраняется. Образцы только в режиме разработки, с маскировкой и удалением через 24 часа |
| Коды подтверждения из уведомлений | Не распознаются и не сохраняются. На Android 15+ система сама скрывает уведомления с одноразовыми кодами от сторонних приложений |
| Чтение базы с украденного или рутованного телефона | База зашифрована SQLCipher, ключ защищён Android Keystore |
| Данные в облачной резервной копии Android | База и настройки исключены из автобэкапа (`dataExtractionRules`) |
| Посторонний открыл приложение на разблокированном телефоне | Вход по биометрии или PIN, блокировка при уходе в фон |
| Отправка финансовых данных стороннему сервису | ИИ выключен по умолчанию, в модель уходят только результаты инструментов, есть режим без названий магазинов |
| Перехват трафика к модели | Только HTTPS. Российский корневой сертификат доверяется только для доменов GigaChat |
| Утечка ключа GigaChat через репозиторий | Ключ вводится пользователем и хранится зашифрованным, в коде и `local.properties` его нет |
| Логи с персональными данными | Суммы, магазины и тексты не пишутся в Logcat в release-сборке |

### 10.3 Чего приложение не делает

- не подключается к банку и не хранит данные для входа в банк;
- не читает SMS (`READ_SMS` не запрашивается);
- не отправляет данные никуда, кроме модели ИИ, и только когда пользователь её включил;
- не содержит аналитики и рекламы.

## 12. Нефункциональные требования

### NFR-01. Производительность

- Главный экран открывается с актуальной суммой быстрее чем за 1 секунду на устройстве среднего уровня.
- Операция из уведомления появляется в приложении и виджете в течение 3 секунд.
- База на 50 000 операций не замедляет списки и статистику заметно для пользователя.

### NFR-02. Надёжность

- Расчёт «можно сегодня» детерминирован и покрыт тестами на границы: последний день периода, смена месяца, перерасход, доход внутри периода, оплата обязательного платежа.
- Миграции Room покрыты тестами, данные не теряются при обновлении.
- Сбой парсера на неизвестном формате не роняет сервис, уведомление просто пропускается.

### NFR-03. Приватность

Все требования раздела 10. Без интернета приложение работает полностью, кроме ИИ.

### NFR-04. UX и доступность

- Светлая и тёмная тема, Material 3.
- Поддержка TalkBack: суммы озвучиваются полностью («четыреста пятьдесят рублей»).
- Крупный шрифт не ломает главный экран.
- Сумма «можно сегодня» понятна без объяснений: цвет плюс текст, а не только цвет.

### NFR-05. Совместимость

- Android 10–17 (API 29–37).
- Проверка на эмуляторах API 29 и API 37 и на реальном телефоне с банковским приложением.

## 13. Тестирование

### 13.1 Unit-тесты

- `BudgetCalculator`: все формулы FR-03 и граничные случаи.
- Парсеры банков: набор реальных текстов уведомлений (замаскированных) как фикстуры, включая отмены, возвраты и неизвестные форматы.
- Дедупликация.
- Сверка: ожидаемый остаток, порог расхождения, корректировка в обе стороны, новая точка отсчёта, несколько карт, уведомления без остатка.
- Цикл ИИ: вызов функций, ограничение числа вызовов, обработка ошибок, через Ktor MockEngine.

### 13.2 Тесты UI и интеграции

- Главный экран: пересчёт после добавления операции.
- Черновики: подтверждение и запоминание правила.
- Миграции Room.
- Сервис уведомлений: обработка пакета банка и игнорирование чужого пакета (instrumented-тест).

## 14. Критерии готовности версии 1.0

- Главный экран корректно показывает «можно сегодня» во всех граничных случаях FR-03.
- Покупка по карте поддерживаемого банка появляется в приложении автоматически, без ручного ввода.
- Чужие уведомления не сохраняются нигде, это проверено тестом.
- База зашифрована, исключена из облачного бэкапа, вход защищён.
- ИИ отвечает на вопросы из FR-08 через инструменты и не получает базу целиком.
- Виджет работает и обновляется.
- Списания и пополнения поддерживаемого банка попадают в приложение автоматически, расхождение с остатком банка обнаруживается и исправляется по сценарию 5.9.
- Все тесты проходят на API 29 и API 37.

## 15. Что не входит в версию 1.0

- несколько валют;
- несколько пользователей и семейный бюджет;
- синхронизация между устройствами и облачный бэкап;
- подключение к банкам по API;
- чтение SMS;
- изменение данных через ИИ;
- инвестиции, кредиты, долги;
- поддержка больше одного банка (архитектура готова, парсеры добавляются позже).

## 16. Этапы реализации

Каждый этап оформляется отдельным OpenSpec change.

1. **establish-foundation:** проект, пакеты, Hilt, тема, навигация, тесты API 29/37.
2. **add-operations-and-categories:** Room, операции, категории, ручной ввод, список.
3. **add-period-and-daily-limit:** период, обязательные платежи, `BudgetCalculator`, главный экран. После этого этапа приложением уже можно пользоваться каждый день.
4. **add-statistics:** диаграммы и итоги периодов.
5. **add-data-protection:** SQLCipher, Keystore, исключение из бэкапа, вход по биометрии.
6. **add-notification-import:** сервис, парсер первого банка, черновики, дедупликация, режим сбора образцов.
7. **add-balance-reconciliation:** остаток из уведомлений, `BalanceReconciler`, плашка расхождения, корректировки, ручная сверка.
8. **add-auto-categorization:** правила по магазинам.
9. **add-widget-and-reminders:** Glance, WorkManager, уведомления приложения.
10. **add-ai-assistant:** `LlmProvider`, клиент GigaChat, инструменты, чат.
11. **add-animations:** анимации интерфейса: изменение сумм и полосок, появление плашек, переходы между экранами; учёт системной настройки «Убрать анимацию».
12. **harden-and-release-v1:** доступность, производительность, проверка безопасности, экспорт и резервная копия.

## 17. Открытые вопросы

1. ~~Какой банк поддержать первым?~~ Решено: первым Сбер, затем Т-Банк и Альфа-Банк. Тексты уведомлений для парсера собираются режимом сбора образцов в самом приложении.
2. Финальное название приложения.
3. Доход регулярный (стипендия, зарплата) или нерегулярный? От этого зависит, как начинать новый период.
4. ~~Несколько карт и счетов учитывать как один общий бюджет или раздельно?~~ Решено: один общий бюджет, сверка с банком — отдельно по каждой карте. Переводы между своими счетами в разных банках не считаются ни тратой, ни доходом: пара «ушло — пришло» склеивается сама, одна сторона отмечается кнопкой «Это перевод себе», отправитель запоминается.
5. Публиковать ли приложение (RuStore, F-Droid) и открывать ли исходный код?
6. Пишет ли первый банк остаток в уведомлениях? Если нет, остаётся только ручная сверка. Пока известно: в двух настоящих уведомлениях Альфа-Банка (списание со счёта и зачисление по СБП) остатка нет; настоящих образцов Сбера и Т-Банка ещё нет.
7. ~~Поддерживать ли SMS банка через уведомление SMS-приложения?~~ Решено: нет, обрабатываются только push-уведомления банковских приложений.
