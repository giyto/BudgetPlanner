## Context

После этапа `add-statistics` база Room версии 2 (`budget.db`) лежит на телефоне открытым файлом SQLite: её фабрика открытия — `FrameworkSQLiteOpenHelperFactory` в `DatabaseModule` с пометкой «заменит SQLCipher». Настройки (расписание дохода, id демо-данных) — в DataStore `settings`. В манифесте `allowBackup="true"`, а `backup_rules.xml` и `data_extraction_rules.xml` — пустые шаблоны, то есть база и настройки сейчас попадают в облачный бэкап Google. `MainActivity` — `ComponentActivity`, весь интерфейс — `BudgetApp()`; пока неизвестно, пройден ли онбординг, виден только фон окна. У пользователя на телефоне уже есть настоящие данные, поэтому старую базу нужно перенести, а не создать заново.

Решения пользователя: вход через системную разблокировку телефона (без своего PIN), таймаут по умолчанию 1 минута, `FLAG_SECURE` по умолчанию выключен, при потере ключа — экран «Начать заново».

## Goals / Non-Goals

**Goals:**
- Файл базы на диске нечитаем без ключа, а ключ нельзя вынуть с телефона (Keystore).
- Обновление приложения не теряет данные: открытая база переносится в зашифрованную один раз.
- Ни база, ни ключ, ни настройки не уходят в облако и на новое устройство.
- Посторонний на разблокированном телефоне не видит суммы без отпечатка или PIN телефона.
- Главный экран по-прежнему открывается быстрее 1 секунды (NFR-01).

**Non-Goals:**
- Защита от владельца рутованного телефона во время работы приложения: ключ в памяти процесса, это вне модели угроз ТЗ.
- Свой PIN приложения, «удалить все данные» в настройках (этап 11), резервная копия (этап 11).
- Шифрование DataStore: в нём нет финансовых данных, только расписание дохода, флаги и id демо-записей; он исключается из бэкапа.

## Decisions

### 1. Ключ базы: случайные 32 байта, обёрнутые ключом Keystore
`DatabaseKeyStore` в `data/security`:
- При первом запуске генерирует 32 случайных байта (`SecureRandom`) — это ключ базы.
- В Android Keystore создаётся ключ AES-256 `budget_db_wrap` с режимом GCM, без `setUserAuthenticationRequired`: он не зависит от блокировки экрана и не сбрасывается при смене PIN или отпечатков. Ключ базы шифруется им, в файл `noBackupFilesDir/db_key.bin` записываются версия формата, IV и шифротекст (`AtomicFile`, чтобы оборванная запись не испортила файл).
- При запуске файл читается и расшифровывается синхронно (доли миллисекунды), ключ живёт только в памяти процесса.
- База открывается сырым ключом SQLCipher (строка `x'<64 hex>'`), а не паролем: так SQLCipher пропускает PBKDF2 на 256 000 итераций при каждом открытии, ключ и так случайный.
- *Альтернатива:* хранить обёрнутый ключ в DataStore, как в черновике. DataStore асинхронный, а ключ нужен до открытия базы; файл в `noBackupFilesDir` читается синхронно и система сама не включает эту папку в бэкап.
- *Альтернатива:* `EncryptedSharedPreferences` из `security-crypto`. Библиотека объявлена устаревшей, а нужное ей — 30 строк своего кода.

### 2. Проверка базы до показа интерфейса
`DatabaseEncryption.prepare()` выполняется один раз при запуске в фоне, до первого обращения к Room, и возвращает `DatabaseState`:
- `Ready` — ключ есть, база открывается (или файла базы ещё нет — первая установка);
- `Migrated` — была открытая база, перенесена (для теста и лога, для интерфейса это то же `Ready`);
- `KeyLost` — файл базы есть и зашифрован, но ключа точно нет или он не подходит: ключа Keystore нет, расшифровка файла ключа не прошла проверку подлинности (`AEADBadTagException`) или SQLCipher ответил SQLITE_NOTADB (`SQLiteNotADatabaseException`);
- `Error` — временный сбой (ошибка Keystore на части прошивок, ввод-вывод, база занята, нет места для файла ключа): данные, скорее всего, целы, поэтому показывается экран с кнопкой «Попробовать снова» и без удаления. Если при этом на диске ещё открытая база, приложение просто работает с ней, как при неудачном переносе.

`MainActivity` до готовности показывает фон окна, как сейчас до загрузки онбординга. При `KeyLost` вместо `BudgetApp` показывается экран потери ключа (решение 4). Room-синглтон строится как раньше, но `SupportOpenHelperFactory` получает ключ из `DatabaseKeyStore`, а первый запрос к базе случается только после `Ready`.
- *Альтернатива:* ловить исключение SQLCipher в репозиториях. Ошибка всплыла бы в случайном экране посреди навигации; проверка при запуске даёт одно место и один экран.

### 3. Перенос открытой базы
Признак открытой базы — первые 16 байт файла равны `SQLite format 3\0` (у SQLCipher заголовок зашифрован). Перенос:
1. Открыть `budget.db` через SQLCipher без ключа (он читает обычный SQLite).
2. `ATTACH DATABASE 'budget.db.enc' AS encrypted KEY "x'…'"`, `SELECT sqlcipher_export('encrypted')`, затем `PRAGMA encrypted.user_version = <user_version исходной>` — `sqlcipher_export` переносит таблицы (включая `room_master_table`) и индексы, но не номер версии, без него Room запустит миграции заново.
3. `DETACH`, закрыть, проверить, что `budget.db.enc` открывается ключом и число строк в `operations`, `periods`, `planned_payments`, `categories` совпадает.
4. Удалить `budget.db-wal`, `budget.db-shm`, заменить `budget.db` файлом `budget.db.enc` (переименование в той же папке).

Если шаг 3 не прошёл, `budget.db.enc` удаляется, открытая база остаётся как есть, и приложение работает с ней до следующей попытки при следующем запуске (ошибка пишется в лог без данных). Потерять данные из-за неудачного переноса хуже, чем ещё один день без шифрования.
- Перед переносом открытая база должна быть закрыта: проверка идёт до создания Room, поэтому соединений нет.

### 4. Потеря ключа: «Начать заново»
Ключ Keystore не привязан к блокировке экрана, поэтому потеря возможна только при сбое хранилища ключей (некоторые прошивки после обновления или сброса) или при восстановлении файлов с другого телефона. Экран: что произошло, что данные на телефоне прочитать нельзя, и кнопка «Удалить данные и начать заново» с подтверждением. Удаляются файлы базы, `db_key.bin` и ключ Keystore, DataStore очищается через `edit { clear() }` (файл открыт синглтоном, удалять его нельзя). Новый ключ создаёт следующая проверка базы, после неё открывается онбординг; если создать ключ не удалось, виден экран «Попробовать снова». Если выйти без нажатия, данные остаются на диске до решения пользователя.

### 5. Бэкап
- `android:allowBackup="false"` — на API 29–30 это полностью выключает автобэкап и `adb backup`.
- На API 31+ `allowBackup` не влияет на перенос с устройства на устройство, поэтому `data_extraction_rules.xml` исключает домены `root`, `file`, `database`, `sharedpref` и `external` и в `cloud-backup`, и в `device-transfer`. `backup_rules.xml` (API 29–30) исключает то же.
- Перенос ключа на другой телефон всё равно бессмыслен: ключ Keystore не покидает устройство.

### 6. Защита входа: системная разблокировка
`DeviceAuthenticator` (интерфейс в `domain/lock`, реализация `BiometricDeviceAuthenticator` в `ui/lock`):
- `availability()` по `BiometricManager.canAuthenticate(BIOMETRIC_WEAK or DEVICE_CREDENTIAL)`: `Available`, `NoScreenLock` (блокировка экрана не настроена), `Unavailable`. Комбинация `BIOMETRIC_STRONG or DEVICE_CREDENTIAL` и один `DEVICE_CREDENTIAL` не поддерживаются на API 29, а `BIOMETRIC_WEAK or DEVICE_CREDENTIAL` работает на API 29–37. `CryptoObject` не нужен: вход защищает интерфейс, а не ключ базы.
- `authenticate(activity)` показывает `BiometricPrompt` с заголовком «Вход в BudgetPlanner» и возвращает `Success`, `Cancelled` или `Error(message)`. Для `BiometricPrompt` `MainActivity` наследует `FragmentActivity`.
- Включение защиты требует успешной проверки: так пользователь убеждается, что разблокировка работает, а посторонний не включит защиту, чтобы запереть владельца.
- Если защита включена, а блокировку экрана на телефоне потом сняли (`NoScreenLock` при запуске), защита выключается с сообщением на главной. Снять блокировку экрана можно только зная её PIN, поэтому это не обход.
- *Альтернатива:* свой PIN приложения. Отклонено пользователем: хранение PIN, счётчик попыток и «забыл PIN» без выигрыша для одного владельца телефона.

### 7. Когда приложение блокируется
`AppLock` (синглтон в `domain/lock`) держит `locked: StateFlow<Boolean>` и правила:
- холодный старт при включённой защите — заблокировано;
- уход в фон (`onStop` единственной активности, кроме поворота экрана — `isChangingConfigurations`) запоминает момент по монотонным часам `ElapsedClock` (интерфейс, в тестах фейк; `Clock` для этого не годится — пользователь может перевести время). `ProcessLifecycleOwner` не подходит: он сообщает об уходе с задержкой 0,7 с и пропускает быстрый возврат, а «Сразу» должно блокировать и его;
- возврат (`ON_START`): если прошло не меньше таймаута — заблокировать. «Сразу» — таймаут 0;
- пока идёт проверка, уход в фон откладывается: на части телефонов ввод PIN — отдельное окно системы, и с «Сразу» приложение блокировалось бы сразу после успешного входа. Если окно закрылось неуспешно, когда пользователь уже ушёл из приложения, отложенное время засчитывается.

Настройки защиты (`enabled`, `timeout`, `hideInRecents`) — в DataStore `settings` через `LockSettingsStore`, по умолчанию выключено, 1 минута, без скрытия. Пока настройки не прочитаны, виден только фон окна, поэтому содержимое не мелькает перед экраном блокировки.

### 8. Экран блокировки
Пока `locked`, `MainActivity` показывает `LockScreen` вместо `BudgetApp` — содержимое приложения не компонуется, поэтому TalkBack и снимок экрана не видят сумм. Чтобы после разблокировки пользователь вернулся на тот же экран, `BudgetApp` обёрнут в `SaveableStateHolder.SaveableStateProvider`: при уходе из композиции его сохраняемое состояние (стек `NavController`, прокрутка, вкладка) остаётся в держателе, а ViewModel экранов — в хранилище активности. Проверка — UI-тест «после разблокировки открыт тот же экран».
- *Альтернатива:* рисовать экран блокировки поверх работающего `BudgetApp` и прятать его от TalkBack. Проще, но содержимое продолжает жить под непрозрачным слоем, и любая ошибка слоёв показывает суммы.
- Вид: графитовый фон главной карточки (`#191C1F` / `#23272C`), иконка кольца, «BudgetPlanner заблокирован», внизу под пальцем большая кнопка «Разблокировать». Проверка запускается сама при появлении экрана и при возврате в приложение, а также если окно закрыла система (`ERROR_CANCELED`); после «Отмены» пользователем остаётся кнопка. Если состояние активности уже сохранено, `BiometricPrompt` молча не показывается — тогда проверка откладывается до возврата. Макеты: `docs/design/screenshots/LockScreen.png` и `DarkLockScreen.png`, шаг онбординга, раздел настроек и экран потери ключа — там же (`OnboardingProtection`, `SettingsProtection`, `KeyLost`), исходник `docs/design/mockups/DataProtection.html`.
- «Назад» на экране блокировки сворачивает приложение, а не открывает содержимое.

### 9. Скрытие в недавних
`hideInRecents` ставит `WindowManager.LayoutParams.FLAG_SECURE` на окно `MainActivity` и снимает его при выключении, сразу, без перезапуска. Флаг одновременно запрещает скриншоты — это сказано в подписи переключателя. По умолчанию выключено.
- Без флага снимок в недавних приложениях может показать последний экран с суммами, даже если приложение потом заблокируется по таймауту. Это компромисс, выбранный пользователем; в подписи настройки это объяснено.

### 10. Онбординг и настройки
- Шаг `PROTECTION` после `PAYMENTS`: «Защитить вход?», объяснение (отпечаток, лицо или PIN телефона; приложение не хранит их), кнопки «Включить» и «Не сейчас». «Включить» запускает проверку; после успеха защита включается и онбординг завершается. Если блокировки экрана нет — вместо «Включить» кнопка «Настроить блокировку экрана» (`Settings.ACTION_SECURITY_SETTINGS`) и подсказка; после возврата доступность проверяется заново. Данные онбординга записываются, как и раньше, одним действием в конце, теперь на этом шаге. На этапе 6 шаг автоимпорта встанет перед ним, как в сценарии 5.1.
- В настройках раздел «Защита входа»: переключатель «Вход по отпечатку или PIN», «Блокировать» (сразу / через 1 минуту / через 5 минут, виден только при включённой защите), переключатель «Скрывать в недавних и запретить скриншоты». Выключение защиты тоже требует проверки.

### 11. Тесты
- Keystore и SQLCipher есть только на устройстве, поэтому `DatabaseKeyStore`, перенос и `KeyLost` — instrumented-тесты на файлах во временной папке.
- `AppLock` — unit-тесты с фейковыми `ElapsedClock` и событиями жизненного цикла.
- UI-тесты онбординга, настроек и экрана блокировки — с фейковым `DeviceAuthenticator` в `TestAppModules` (системный диалог Compose-тесты не нажимают). Настоящий `BiometricPrompt` проверяется вручную на эмуляторе с отпечатком и на телефоне.
- Остальные instrumented-тесты продолжают использовать базу в памяти без шифрования; тест скорости на 50 000 операций дополнительно запускается на зашифрованной базе в файле.

## Risks / Trade-offs

- [Скорость SQLCipher] Шифрование страниц замедляет запросы на 5–15 % → сырой ключ без PBKDF2, тест скорости агрегатов на зашифрованной базе (< 1 с), проверка времени открытия главной.
- [Сбой переноса оставит базу открытой] → перенос с проверкой числа строк и повтором при следующем запуске; данные важнее одного дня без шифрования.
- [Потеря ключа Keystore на отдельных прошивках] → ключ без привязки к блокировке экрана; экран «Начать заново» вместо падения; резервная копия на этапе 11.
- [Снимок в недавних без `FLAG_SECURE`] → выбор пользователя, объяснён в подписи настройки.
- [`MainActivity` → `FragmentActivity`] → поведение Compose не меняется; проверяется полным набором UI-тестов на API 29 и 37.
- [R8 в release-сборке вырежет классы SQLCipher, вызываемые из нативного кода] → проверить `assembleRelease` и запуск release-сборки; при необходимости добавить keep-правила.

## Migration Plan

Первый запуск после обновления переносит открытую базу (решение 3), пользователь ничего не делает. Отката нет: старая версия приложения не откроет зашифрованную базу, поэтому установка более старой сборки поверх новой требует удаления данных — для приложения без публикации это приемлемо.
