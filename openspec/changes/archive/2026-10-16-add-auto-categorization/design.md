## Context

Мотивация — в `proposal.md`, требования — в `specs/`. Что уже есть:

- `ImportNotification.importNew` по виду уведомления выбирает тип и предварительную категорию (`other_expense`, `transfers`, `other_income`), проверяет дубли, склеивает пару перевода себе, проверяет запомненные свои имена (`AutoImportSettings.ownNames`, нормализация `normalizeForSearch`) и создаёт черновик (`isDraft = true`).
- `ConfirmDrafts` по выбору пользователя подтверждает черновики одной транзакцией (`OperationRepository.confirmDrafts`) и выводит тип из категории (`isTransfers` → `TRANSFER`).
- Экран черновиков (`ui/drafts/DraftsScreen.kt`) хранит выбор в `MutableStateFlow<Map<Long, Long>>`, подпись «По типу операции» показывается у перевода, пока пользователь не выбрал категорию. Галочки «Запомнить» нет, хотя она есть на макете `Drafts`.
- Категории: свою пустую можно удалить, категорию по умолчанию — только скрыть (spec `categories`). Ключи категорий по умолчанию: `products`, `cafe`, `transport`, `connection`, `entertainment`, `clothes`, `health`, `subscriptions`, `transfers`, `other_expense` и доходные.
- База Room версии 5.

## Goals / Non-Goals

**Goals:**
- Поиск правила одним запросом по индексу при каждом импорте.
- Нормализация и словарь — чистые функции в `domain`, покрытые unit-тестами.
- Ни одно правило не применяется к переводам себе и не мешает их склейке.

**Non-Goals:**
- Правила для ручного ввода: категория при ручном вводе выбирается как раньше (частые сначала).
- Правила по сумме, времени или банку; регулярные выражения от пользователя.
- Пересчёт уже сохранённых операций при изменении или удалении правила.
- Подсказка ИИ — этап `add-ai-assistant`.
- Обновление словаря из интернета: словарь встроен в приложение.

## Decisions

### 1. Ключ магазина — нормализованное название, отдельно для трат и доходов

`MerchantKey.of(name): String?` в `domain/categorize`: нижний регистр, «ё» → «е», кавычки «»"' и знаки `*.,;:` → пробел, слова с цифрами удаляются, пробелы схлопываются; пустой результат — `null`. Отличается от `normalizeForSearch` удалением слов с цифрами: для поиска по операциям номер терминала полезен, для правила — мешает. Правило ищется по паре (ключ, вид категории), потому что одно имя может быть и получателем перевода, и отправителем зачисления.

*Альтернатива:* сравнивать по началу строки (`startsWith`). Отвергнута: «Пятёрочка» и «Пятёрочка у дома» — разные строки, но префиксы ломаются на перестановке слов и на хвостах вроде «MOSCOW RUS» в начале.

### 2. Таблица `category_rules`

Колонки: `id`, `merchant_key` (TEXT), `category_kind` (TEXT), `category_id` (FK на `categories`, `ON DELETE CASCADE`), `merchant_display` (TEXT, как показывать в списке — название из последнего подтверждения), `updated_at`. Уникальный индекс (`merchant_key`, `category_kind`), индекс по `category_id`. Запоминание — поиск по уникальному индексу и вставка или обновление в одной транзакции DAO (`@Upsert` здесь не подходит: он сравнивает по первичному ключу). Миграция 5 → 6 создаёт таблицу; каскадное удаление выполняет требование «при удалении своей категории её правила удаляются» без отдельного кода.

### 3. Порядок проверок в импорте

`importNew`: тип и предварительная категория → дубли → склейка пары перевода себе → своё имя → **правило** → **словарь** → черновик. Правило и словарь стоят после логики переводов себе, чтобы правило «Олег К. → Кафе» не мешало склейке пары, если «Олег К.» на самом деле второй банк пользователя. Тип по правилу: для `PURCHASE`/`TRANSFER_OUT` — `TRANSFER`, если категория правила «Переводы», иначе `EXPENSE`; `REFUND` и `INCOME` сохраняют свой тип. Скрытая категория правила игнорируется — операция становится черновиком.

### 4. Словарь — объект Kotlin в `domain/categorize/MerchantDictionary`

Список записей «ключевые слова → ключ категории по умолчанию» (`products`, `cafe`, `transport`, `connection`, `health`, `clothes`, `subscriptions`, `entertainment`). Ключевая фраза совпадает целыми словами нормализованного названия; названия со словом «банк» словарь не трогает (`yandex*go` → `yandex go` → совпадает «yandex go»; «пятерочка», «pyaterochka»; слова с цифрами вроде «5ka» нормализация отбрасывает, их в словаре нет). Порядок записей значим: более длинные фразы проверяются раньше («яндекс еда» — кафе, раньше чем «яндекс» вообще; одиночное «яндекс» в словаре нет). Категория ищется по `default_key`; если пользователь скрыл её, подсказки нет. Начальный набор — около 60 записей популярных в России сетей и сервисов; пополняется кодом.

*Альтернатива:* JSON-файл в ресурсах. Отвергнута: словарь нужен в чистом `domain` и в unit-тестах без Android.

### 5. Подпись «Знакомый магазин» — вычисляется при показе, а не хранится

Экран черновиков показывает подпись, если пользователь ещё не выбрал категорию сам и предварительная категория совпадает с категорией словаря для этого магазина. Так не нужна колонка «источник подсказки» в `operations`, а после смены категории пользователем подпись исчезает сама. Логика — в use case `DraftHint` (`domain`), экран получает готовый признак.

### 6. Запоминание при подтверждении

Перевод или зачисление, сохранённые по правилу, получают исходный тип в `original_type`, а поиск второй стороны перевода себе учитывает и такие операции: правило не мешает склейке, даже если сделало перевод тратой. По новому правилу подтверждаются только покупки и возвраты того же магазина; ожидающие переводы и зачисления остаются черновиками, потому что ещё могут оказаться переводом себе. Подтверждение не перезаписывает операцию, которую импорт успел склеить в перевод себе.


`ConfirmDrafts` получает для каждого выбора признак `remember`. В одной транзакции репозитория: подтверждение выбранных черновиков, запись правил для отмеченных и подтверждение других черновиков того же ключа и вида с той же категорией (spec drafts, «Другие черновики того же магазина»). Тип для подтверждаемых по правилу черновиков выводится так же, как в решении 3. Переводы себе в выбор правил не попадают; галочка у них не показывается.

### 7. Экран правил

Маршрут `CategoryRules`, вход — пункт «Правила для магазинов» в настройках под «Категориями» с числом правил. Список из `observeRules()` с категориями; выбор категории — существующий `CategoryPickerSheet` с категориями того же вида без скрытых; удаление — как удаление операции: строка исчезает, snackbar «Правило удалено · Отменить» 5 секунд, возврат — повторная вставка того же правила.

## Risks / Trade-offs

- [Реальные названия магазинов в уведомлениях пока неизвестны: у Альфы и Сбера могут быть хвосты вроде «MOSCOW RUS» или коды без цифр] → такие хвосты сделают разные ключи для одного магазина, правило не сработает и пользователь увидит черновик. Проверка нормализации на собранных образцах — задача в конце этапа; хвосты добавляются в нормализацию по факту.
- [Ложное срабатывание словаря: слово-ключ внутри чужого названия] → совпадение только с началом слова, словарь даёт лишь подсказку в черновике, пользователь её видит и может сменить.
- [Правило создаёт неверную категорию надолго] → правила видны и меняются в настройках; операция по правилу видна в списке операций, её можно отредактировать.
- [Подтверждение других черновиков того же магазина может удивить] → это видно сразу на том же экране: карточки исчезают вместе, сценарий описан в спецификации.
