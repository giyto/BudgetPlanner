## Context

Мотивация — в `proposal.md`, требования — в `specs/`. Что уже есть после `add-notification-import`:

- Парсеры возвращают `ParsedNotification.balance` (регулярка «баланс | доступно | остаток»), `ImportNotification` сохраняет его в таблицу `bank_balances` (`bank_id`, `card_last4`, `balance_kopecks`, `observed_at`) для всех уведомлений, кроме дублей. Таблица пока нигде не читается.
- У операции есть `bank_id`, `card_last4`, `occurred_at` (epoch millis), `is_draft`, `source` (`MANUAL`, `NOTIFICATION`). Перевод себе (`OWN_TRANSFER`) хранит направление основной стороны в `original_type` (`TRANSFER` — ушли, `INCOME` — пришли), вторую сторону — в `counter_bank_id`, `counter_card_last4`, `counter_occurred_at`.
- Время у операции из уведомления и у остатка из того же уведомления одно и то же: `parsed.occurredAt` (время публикации уведомления).
- Импорт идёт последовательно под `Mutex` в `NotificationIntake`. База Room версии 4, зашифрована SQLCipher.
- В двух настоящих уведомлениях Альфы остатка нет (открытый вопрос 6), формат с остатком известен только по описанию.

## Goals / Non-Goals

**Goals:**
- Сверка по каждому счёту, устойчивая к порядку операций, черновикам и переводам себе.
- Расчёт ожидаемого остатка одним запросом к базе, без загрузки всех операций в память.
- Вся логика сверки в чистом Kotlin в `domain`, проверяемая unit-тестами на фейковых репозиториях.
- Возможность пройти весь сценарий на эмуляторе без настоящих банковских операций.

**Non-Goals:**
- Уведомление приложения о расхождении — этап `add-widget-and-reminders`.
- Поле «счёт» в обычном редакторе операции: счёт задаётся только при добавлении из отфильтрованного списка.
- Кредитные карты и лимиты: если банк пишет «доступно» вместе с кредитным лимитом, сверка будет постоянно расходиться (см. риски).
- История сверок: хранится только текущее состояние и время последней сверки.

## Decisions

### 1. Ключ счёта — пара (банк, цифры), «Счёт без автоимпорта» — пара (пусто, пусто)

`ReconAccount(bankId: String?, cardLast4: String?)`. В таблицах ключевые колонки хранят пустую строку вместо `null`, чтобы уникальный индекс работал (в SQLite `NULL` не равен `NULL`). Операции без цифр относятся к счёту так (spec «Счета для сверки»):

- у банка нет ни одного счёта с цифрами — к счёту `(bank, "")`;
- у банка ровно один счёт с цифрами — к нему;
- счетов с цифрами несколько — ни к одному.

Список счетов банка берётся из `reconciliation_accounts` и `bank_balances`. Правило применяется в запросе ожидаемого остатка параметром «включать операции без цифр».

*Альтернатива:* запрещать сверку банков без цифр. Отвергнута: ТЗ прямо требует считать такие операции одной картой.

### 2. Состояние сверки — отдельная таблица `reconciliation_accounts`

Колонки: `bank_id` (TEXT, '' — без банка), `card_last4` (TEXT, ''), `anchor_kopecks`, `anchor_at`, `pending_bank_kopecks` (nullable), `pending_expected_kopecks`, `pending_at`, `last_reconciled_at`. Уникальный индекс по (`bank_id`, `card_last4`). Расхождение — это строка с непустым `pending_bank_kopecks`.

*Альтернатива:* вычислять расхождение на лету из `bank_balances` при каждом показе главной. Отвергнута: решение пользователя («пропустить») нужно где-то запоминать, а пересчёт на каждом кадре дороже одной строки.

### 3. Ожидаемый остаток — сумма одним SQL-запросом по полуинтервалу (anchor_at, at]

```
expected = anchor + Σ знак(op) × amount
  по операциям счёта: anchor_at < occurred_at ≤ at, source ≠ ADJUSTMENT
  + Σ по OWN_TRANSFER, где счёт — вторая сторона: anchor_at < counter_occurred_at ≤ at
```

Знак: `INCOME`, `REFUND` — плюс; `EXPENSE`, `TRANSFER` — минус; `OWN_TRANSFER` основной стороны — по `original_type`, второй стороны — противоположный. Черновики входят (они уже в бюджете). Строгое `>` для `anchor_at` исключает операцию, которая пришла вместе с остатком точки отсчёта; нестрогое `≤` для `at` включает операцию из уведомления с новым остатком (spec «Покупка в уведомлении с остатком»). Запрос возвращает `Long` в копейках; знак вычисляется в `CASE` внутри SQL, `domain` получает только итог через `ReconciliationRepository.netChange(account, from, to, includeNoDigits)`.

*Альтернатива:* хранить «текущий расчётный остаток» и менять его при каждой операции. Отвергнута: правка и удаление операций, склейка и расклейка переводов себе потребовали бы обновлять его в десятке мест.

### 4. Корректировка — новый источник `OperationSource.ADJUSTMENT`, а не новый тип

Тип остаётся `EXPENSE` или `INCOME`, поэтому `BudgetCalculator`, статистика и список работают без изменений, а «входит в можно сегодня как обычная операция» выполняется само. Категория — «Другое» или «Другие доходы» (ключи `other_expense` и `other_income`, как у предварительных категорий автоимпорта). Название — «Корректировка», банк и цифры — счёта, время — момент решения, `is_draft = false`. В ожидаемый остаток корректировки не входят (решение 3), поэтому её время относительно новой точки отсчёта не важно и двойного учёта нет. `source` хранится строкой, схема колонки не меняется.

*Альтернатива:* новый `OperationType.ADJUSTMENT`. Отвергнута: пришлось бы учить ему расчёт, статистику, фильтры и редактор, хотя по смыслу это обычная трата или доход.

### 5. `BalanceReconciler` — чистая функция, сценарии — use case'ы

`BalanceReconciler.evaluate(anchor, netChange, bankBalance): Result` (`Matched` или `Mismatch(expected, diff)`; порог `|diff| > 100` копеек). Use case'ы в `domain/usecase/Reconciliation.kt`:

- `ReconcileBalance(account, balance, at)` — вызывается из `ImportNotification` после `addBalance`, внутри того же импорта под `Mutex`. Нет точки отсчёта — создать; авто-сверка выключена — только сохранить остаток; иначе сравнить от точки отсчёта и записать `Matched` (сдвиг точки отсчёта, `last_reconciled_at`) или `pending`.
- `RecheckMismatch(account)` — при возврате на экран сверки: пересчитать `pending` по тому же остатку банка с текущими операциями.
- `ResolveMismatch(account, Adjust | Skip)` — корректировка в одной транзакции с переносом точки отсчёта на `pending_bank`/`pending_at`.
- `ManualReconcile(account, amount)` — время берётся из `Clock`; дальше как `ReconcileBalance`.
- `ObserveMismatches()` и `ObserveLastReconciliation()` — `Flow` для главной и экрана периода.
- `SetAutoReconcile(enabled)` — при включении точка отсчёта каждого счёта переносится на его последний остаток из `bank_balances`, `pending` очищается.

Корректировка и перенос точки отсчёта пишутся в одной транзакции Room (`withTransaction` в реализации репозитория), чтобы при сбое не появилась корректировка без закрытого расхождения.

### 6. Настройка — DataStore, ключ `auto_reconcile` (по умолчанию `true`)

Как остальные пользовательские настройки (`AutoImportSettings`). Плашка на главной комбинирует `ObserveMismatches()` с этим флагом, поэтому выключение скрывает расхождения сразу, а данные не теряются до решения при повторном включении (решение 5 их сбрасывает — spec «Сверка снова включена»).

### 7. Экран сверки — один маршрут, два вида

Маршрут `reconcile?bank={bank}&card={card}`. Без аргументов — все счета с расхождением или остатком: если такой один — вид `Reconcile` (карточка «В банке / В приложении / Разница», три варианта радиокнопками и кнопка «Записать корректировку»); если несколько — вид `ReconcileCards` (список карт с «сходится» или разницей и действия для выбранной). Ручная сверка — тот же экран в режиме ввода остатка: выбор счёта (bottom sheet) и поле суммы по правилам ввода сумм из `operations`.

### 8. Фильтр «счёт с даты» — аргументы навигации списка операций

`operations?bank=&card=&from=` — ViewModel добавляет условие к существующему запросу списка (обе стороны перевода себе, правило операций без цифр). Кнопка «+» при активном фильтре передаёт счёт в редактор, ручная операция сохраняется с `bank_id`/`card_last4` и `source = MANUAL`. Чип фильтра стоит перед чипами источника.

### 9. «Фейковый банк» — отдельный модуль `:tools:fakebank`

Обычное Android-приложение с product flavors `sber`, `tbank`, `alfa`, у каждого `applicationId` равен пакету банка из `SupportedBanks`. Экран: список готовых текстов (покупка с остатком, без остатка, зачисление без цифр, перевод себе — тексты как в тестах парсеров, только вымышленные) и поле для своего текста; кнопка публикует уведомление через `NotificationManager`. Модуль не входит в зависимости `:app` и не попадает в его сборку.

Ставится только на эмулятор (`ANDROID_SERIAL=emulator-5554`). На телефон с установленным настоящим банком он не встанет: подпись не совпадает, и Android отказывает в установке поверх. На телефон без этого банка его ставить нельзя: он выдаст себя за банк в списке приложений. Это правило записывается в README модуля.

*Альтернатива:* `adb shell cmd notification post`. Отвергнута: уведомление приходит от пакета `com.android.shell`, а фильтр автоимпорта пропускает только пакеты банков.

## Risks / Trade-offs

- [Банк не пишет остаток (вопрос 6)] → автоматической сверки для его карт не будет, ручная работает всегда; формат с остатком проверяется на образцах, когда они появятся.
- [«Доступно» включает кредитный лимит] → постоянное расхождение у кредитных карт. Пользователь может нажать «Пропустить» или выключить авто-сверку; отдельная поддержка кредитных карт — вне этапа.
- [Уведомления приходят не по порядку: остаток раньше более ранней покупки] → операция окажется до точки отсчёта и не попадёт в расчёт, появится ложное расхождение. Время берётся из времени публикации уведомления, а не из времени обработки, это снижает риск; ложное расхождение исправляется «Пропустить».
- [Удаление или правка операции после совпадения] → точка отсчёта уже сдвинута, расхождение покажется только при следующем остатке. Это ожидаемо: банк — источник правды на момент сверки.
- [Несколько счетов банка и операции без цифр] → такие операции не входят ни в один счёт, возможны ложные расхождения; на экране сверки их видно в «Найти пропущенную операцию» без фильтра по цифрам — они остаются в общем списке.
- [Фейковый банк на реальном телефоне] → ставится только на эмулятор, правило в README модуля и в tasks; установка поверх настоящего банка невозможна из-за подписи.

## Migration Plan

- Миграция Room 4 → 5: `CREATE TABLE reconciliation_accounts` и уникальный индекс. Существующие строки `bank_balances` не трогаются; первая точка отсчёта появится при следующем остатке или при включении авто-сверки. Тест миграции 4 → 5 рядом с тестами 2 → 3 и 3 → 4.
- Откат — переустановка предыдущей версии с очисткой данных (понижение версии базы Room не поддерживает); для личного приложения на одном телефоне это приемлемо.
