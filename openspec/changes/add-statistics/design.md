## Context

После этапа `add-period-and-daily-limit` в базе Room версии 2 есть операции с `local_date` и индексами по `local_date` и `category_id`, категории, периоды (у завершённых `end_date` — день начала следующего) и обязательные платежи с днём оплаты. `BudgetCalculator` считает статус периода на любой день. Вкладка «Статистика» — заглушка в графе `StatsGraph`. В теме уже есть токены диаграмм (`chartBarOver` и цвета категорий). Требования этапа — в spec `statistics` и изменении `app-navigation`; решения пользователя (сравнение «те же дни от начала», 7 дней с прокруткой, цвет по лимиту своего дня, итоги периодов со статистикой каждого) — в proposal.md.

## Goals / Non-Goals

**Goals:**
- Агрегаты, которые этап 10 отдаст ИИ-инструментам без переделки: чистые функции в домене плюс запросы в репозитории.
- Экран, который на 50 000 операций не грузит операции в память.
- Одни и те же блоки для текущего режима и для завершённого периода.

**Non-Goals:**
- Переход из диаграммы к списку операций категории, листание прошлых календарных месяцев, экспорт (этап 11).
- Статистика доходов: FR-07 говорит только о расходах.

## Decisions

### 1. Диапазон дат как основа всех агрегатов
`DateRange(start, endInclusive)` в домене. Режим «Период» — `period.startDate..today`, «Месяц» — `today.withDayOfMonth(1)..today`, завершённый период — `startDate..endDate − 1` (у завершённого `end_date` — первый день следующего). Все запросы принимают диапазон в днях от эпохи, как `local_date`.
- Прошлый диапазон для сравнения (`previousRange`): для периода — первые N дней предыдущего периода, где N — длина текущего диапазона, но не дальше конца предыдущего периода; для месяца — те же числа прошлого месяца, обрезанные по его длине. Предыдущий период текущего — тот, у которого `end_date` равен началу текущего; если такого нет, сравнения нет.
- *Альтернатива:* передавать в запросы период целиком. Диапазон один на все режимы и подходит ИИ-инструментам с произвольными датами.

### 2. Агрегаты — запросы Room с группировкой
Новый `StatisticsRepository` в домене и `RoomStatisticsRepository` на `StatisticsDao`:
- `spendingByCategory(range)`: `GROUP BY category_id` с суммой `CASE type WHEN 'EXPENSE' THEN amount WHEN 'TRANSFER' THEN amount WHEN 'REFUND' THEN -amount ELSE 0 END`, только по `local_date BETWEEN`;
- `spendingByMerchant(range, limit)`: то же по `merchant IS NOT NULL`, с числом операций, `ORDER BY total DESC LIMIT`;
- `spendingByDay(range)`: `GROUP BY local_date` для режима «Месяц»;
- `totals(range)`: доходы и траты одной строкой для итогов периодов.

Все запросы — `Flow`, поэтому экран обновляется при изменении операций. Индекс `local_date` уже есть, миграция не нужна. Скорость проверяется instrumented-тестом на 50 000 операций.
- *Альтернатива:* загрузить операции диапазона и считать в Kotlin. Для месяца это сотни строк, но для ИИ-инструментов «за год» и для 50 000 операций — лишняя память; SQL-группировка дешевле и проверяется тем же тестом.

### 3. Траты по дням периода — через `BudgetCalculator`
Цвет дня зависит от лимита того дня, а лимит — от трат до него, резерва на начало дня и оплат платежей. Повторять это в SQL нельзя без второй реализации FR-03, поэтому `DailySpending.forPeriod(period, operations, payments, today)` в `domain/stats` вызывает `BudgetCalculator.calculate` для каждого дня периода по сегодня и берёт `dailyLimit` и `spentToday` (траты дня без оплат в пределах резерва). Для периода в 30 дней с сотнями операций это доли миллисекунды. Операции периода уже приходят из `OperationRepository.observeFrom`.
- Ограничение: платёж, удалённый после оплаты, не восстанавливается для прошлых дней — его лимит считается по текущему списку платежей. Для статистики это допустимо.
- Режим «Месяц» охватывает несколько периодов, лимита у него нет: столбики из `spendingByDay`, без линии.
- *Альтернатива:* сравнивать все дни с сегодняшним лимитом. Отклонено пользователем: прошлые дни оценивались бы по чужому лимиту.

### 4. Доли категорий и «Остальное» — чистая функция
`CategoryBreakdown.of(totals, categories)` в `domain/stats`: отбрасывает суммы ≤ 0, сортирует по убыванию (при равенстве — по порядку категорий), при числе категорий больше пяти оставляет четыре и сводит остальные в «Остальное». Проценты — метод наибольшего остатка: целые части, затем по единице категориям с наибольшими дробными остатками, чтобы сумма была ровно 100. «Остальное» — не категория, а отдельный элемент без id с серым цветом.

### 5. Сравнение — чистая функция над двумя срезами
`SpendingComparison.of(current, previous, limit = 3)` получает суммы по категориям двух диапазонов и возвращает до трёх изменений с наибольшим `|разница|`, без нулевых. Процент — `разница / прошлое × 100` с округлением к ближайшему целому; при прошлом 0 — признак «новая». Тот же результат отдаст инструмент `compare_periods` на этапе 10.

### 6. Итоги периодов
`ObservePastPeriods` берёт завершённые периоды (`PeriodDao.observeFinished`, новые сверху) и для каждого `totals(range)`: бюджет = стартовая сумма + доходы, потрачено, остаток = бюджет − потрачено. Периодов единицы и десятки, запрос на каждый по индексу дешёвый; итог не хранится, поэтому исправление старой операции меняет его сразу (решение этапа 3).

### 7. Экран и навигация
`StatsViewModel` держит режим в `SavedStateHandle` и собирает `StatsUiState` (диапазон, разбивка по категориям, дни, сравнение, топ магазинов, итоги периодов) из use cases через `flatMapLatest` по режиму и `TodayTicker`. Экран — `LazyColumn` из карточек по макету: переключатель (`SegmentedChoice` из `ui/components`), карточка категорий, «По дням», сравнение, топ магазинов, итоги периодов.
- Статистика завершённого периода — маршрут `PeriodStats(periodId)` поверх разделов, без нижней панели; `PeriodStatsViewModel` использует те же use cases с диапазоном периода и те же composable-блоки, без переключателя и итогов.
- Состояние раздела сохраняется навигацией (графы вкладок с `saveState`), поэтому «Назад» из `PeriodStats` возвращает к той же прокрутке.

### 8. Диаграммы
- Кольцо — `Canvas` с `drawArc` по долям, зазор между сегментами 2°, толщина как в макете; центр — две строки текста, легенда — обычная `Column`. Описание для TalkBack на всей карточке.
- Дни — Vico 3 `CartesianChartHost` со слоем столбиков: цвет столбика задаётся по признаку дня («больше лимита» — `chartBarOver`, иначе `primary`), линия лимита — `HorizontalLine` с подписью. `VicoScrollState` с начальной прокруткой к концу, видимая ширина — 7 столбиков. Подписи оси X — «Пн 12», сегодняшняя полужирная. Описание для TalkBack — текст по всем дням диапазона, потому что столбики на холсте недоступны TalkBack по отдельности.
- *Альтернатива:* столбики тоже на `Canvas`. Vico даёт прокрутку, оси и линию без своего кода, и он уже выбран в ТЗ (9.1); если API Vico 3 не позволит красить столбики по признаку дня, запасной вариант — свой `Canvas` с `horizontalScroll`, решение фиксируется в задаче 6.1.

## Risks / Trade-offs

- [Vico 3 меняет API между минорными версиями] → версия фиксируется в каталоге, код диаграммы в одном файле `ui/stats/DailyChart.kt`.
- [Лимит прошлого дня зависит от текущего списка платежей] → описано в решении 3; влияет только на цвет столбика.
- [Магазинов нет до этапа 6] → блок скрыт, пока нет данных (spec).
- [Длинное описание диаграммы по дням для TalkBack в длинном периоде] → дни с нулевыми тратами объединяются: «с 1 по 3 октября трат нет».
